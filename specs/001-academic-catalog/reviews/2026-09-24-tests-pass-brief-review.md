# Review of the tests pass brief, 2026-09-24

## Verdict and method

Revise the brief before task generation. The owner’s D1–D5 decisions are usable, and the investigation correctly identifies important weak tests and missing guards. The brief turns some useful observations into universal promises that the current contracts cannot meet, and its budget and rehearsal safety rules need sharper boundaries. This was a source review only: I read the brief, investigation, right-sizing guide and `tests/conftest.py` in the requested order, then sampled the cited tests and harnesses. I did not run the suite or inspect owner data. The uncommitted brief was not changed.

The first twelve rows audit specific investigation claims against the named source. “Overstated” means the cited weakness exists but the description would lead an implementer to discard a useful assertion or rewrite too much. The remaining rows test the brief’s scope and execution plan.

## Scope, budget and order

The five dangerous gaps are justified by concrete incidents: a managed PDF must survive source removal, a foreign destination must never be adopted on retry, export blockers must be detected rather than merely enforced, locking must work across processes, and `remove` preview must not mutate state. Add independent assertions for catalog, file bytes and exported bibliography where those are at risk. The brief should also cover the demo’s two empty-list assertions and missing section-count check, and decide whether the real-trial script’s show/search/backup lines are assertions or visible diagnostics. Its “every error code gets a test or is removed” promise is broader than the evidence warrants: some codes are private, unreachable on supported input or already guarded by a stronger boundary test. Give each code a disposition, then test public distinctions that matter.

The investigation’s “about fifteen unit tests filed as contract tests” is a labeling problem with a qualifier: tests calling application services against SQLite are integration tests, not pure units. Relocate only tests whose fixture and subject are actually pure; add selected command-boundary tests for missing options, envelopes and human output. A coverage percentage cannot by itself assign tests to unexecuted branches. The wheel-install gate belongs to the later release pass under D4. Contract updates D2(a), D2(b) and D2(d) are authorized, yet they should not inflate the test rewrite budget or hide a broken public command.

The numerical plan is too precise. Sixty touched could be exceeded by the refusal sweep alone; thirty deletions are speculative because several cited “bad” tests contain useful assertions; forty additions may be consumed by the five dangerous gaps, eight property invariants, lock and restore, command options and demo checks before the rehearsal is counted. One new development dependency is plausible for Hypothesis, subject to the project’s three-day cooldown and lockfile update. Two harness scripts are plausible only if they extend the existing move rehearsal and real-trial scripts, with the corpus manifest as data rather than another runner. The convention can fit on one page if it stays a decision rule with three examples, not a catalogue of every assertion style. Measure changes after the first cluster and ask the owner for judgment if this becomes a new testing framework rather than a repair pass.

Use this order: (1) write the convention and make the CLI fixture, cwd and isolation deterministic; (2) establish reproducible subprocess coverage and a green baseline, without adding coverage overhead to every ordinary run; (3) add the high-risk missing guards; (4) rewrite weak tests in clusters, removing only duplicate behavior; (5) add bounded generators and a corpus pilot that can reveal which invariants matter; (6) run the full restored-copy rehearsal after its capacity and cleanup checks. The exact phase boundaries can be tasks, not another specification.

## Convention draft (about 150 words)

A test names one behavior and shows the condition that makes it true or false. Its expected result comes from a contract, fixed fixture, independent implementation, or invariant, rather than from the same function on another line. Check the public result and the state that matters: catalog row, file bytes, destination name, or absence of a write. For a refusal, assert the applicable exit code or exception category, the specific error code, and the unchanged state at risk. Change one relevant input to show why the outcome changes, as the duplicate-attachment test does with file content. Inject failures at named boundaries and inspect persisted state after retry, as the interrupted-export test does. For invalid input, use the command boundary when the promise includes CLI behavior, as the capture test does. Keep setup failures visible; do not let either success or refusal satisfy the same case. A generator needs an invariant capable of failing on a wrong result and a small saved example for each real defect it discovers.

## Assumptions and two owner questions

The plan assumes the named external corpora can be obtained, identified and used under their terms; that their entries fit refs’ declared BibTeX, CSL and Zotero input contracts; that a restored CCC copy can be isolated from live paths; that macOS sandboxing and all renderers are present when their checks matter; that subprocess coverage can be combined without making the normal suite unreasonably slow; and that deleting a test never removes the only guard for a requirement. None is established by the investigation’s counts alone. The current 90% combined coverage is a useful baseline, not a reproducible gate until its command, include/exclude settings and subprocess startup are recorded.

2. What exact restored-copy location and cleanup ownership will the owner supply? Should the harness delete only its own derived homes and leave the supplied restored copy for the owner to remove?
