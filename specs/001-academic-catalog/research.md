# Research: Academic Catalog Workflow

**Date**: 2026-09-20

**Status**: Phase 0 decisions complete for implementation planning. Revised after the bibliographic-model review. These are design selections, not claims that the application or live migration has passed acceptance.

**Inputs**: [Specification](spec.md), [constitution](../../.specify/memory/constitution.md), and every document in the [docs index](../../docs/README.md). Three focused research agents investigated bibliography fidelity, transliteration, and filesystem recovery. The five clarification answers take precedence over older proposals for link-in-place defaults, whole-batch rejection, and extra overwrite permission on every export.

## R1. Runtime and dependency scope

**Decision**: Build one Python 3.14 package with a `refs` console entry point. Use Typer 0.27.x for command composition, Pydantic 2.x for strict boundary validation and generated JSON Schema, stdlib `sqlite3` for persistence, `tomllib` for preferences, and ordinary functions/dataclasses for internal transformations. Provisionally select `bibtexparser==2.0.1` for bibliography syntax, subject to the explicit profile fixtures, `pylatexenc~=2.10` for explicit use of TeX text/group parsing, and `Unidecode==1.4.0` behind a versioned name-token policy. Use pytest, pytest-cov, Ruff, and ty for development; exact compatible versions belong in the implementation lockfile. Start with dependency ranges `typer>=0.27,<0.28` and `pydantic>=2.13,<3`; the two semantic conversion packages are pinned until fixture comparisons justify an upgrade.

**Rationale**: This is a local structured CLI with existing Python tooling and substantial file/metadata behavior. Typer provides annotation-driven commands and a testing interface, and follows the user’s explicit design preference; Pydantic provides strict validation and schema generation. Domain operations must not depend on Typer contexts or pass storage connections to providers. The local ad-hoc environment reports Python 3.14.2, SQLite 3.50.4, and FTS5; these observations do not establish the eventual packaged runtime. [Typer release notes](https://typer.tiangolo.com/release-notes/), [strict validation](https://docs.pydantic.dev/latest/concepts/strict_mode/), [JSON Schema generation](https://docs.pydantic.dev/latest/concepts/json_schema/).

**Alternatives considered**: Rust could provide a single binary but adds a separate ecosystem without resolving the bibliography-fidelity work. A web service, ORM, async runtime, workflow engine, and general plugin manager have no initial workflow requirement. Argparse is viable; Typer supplies the preferred command design and established local conventions. Direct Click was superseded by the user’s explicit Typer preference and the [local dependency audit](dependency-audit.md). Handwritten JSON validation would duplicate schema work and error reporting.

**Build policy**: Use uv with a project-local environment, commit `uv.lock` when implementation creates it, and preserve `[tool.uv] exclude-newer = "3 days"`. Verify with `uv sync --locked`; never substitute `--frozen` to hide a configuration mismatch. No project environment or lockfile is created during planning. [uv resolution](https://docs.astral.sh/uv/concepts/resolution/), [locking](https://docs.astral.sh/uv/concepts/projects/sync/).

Use `uv_build>=0.12.1,<0.13` for packaging, following the audited danner/git-muster manifests. The [dependency audit](dependency-audit.md) records sample selection, package counts, version evidence, and why unrelated sibling dependencies are not added.

## R2. Authoritative data, transactions, and search

**Decision**: Store normalized records, relationships, original input bytes, provenance, operation outcomes, and recovery intents in one local SQLite database. Use explicit short write transactions, foreign keys, uniqueness constraints, integer revisions, and request fingerprints. Start with rollback journaling and `synchronous=FULL`; set a five-second busy timeout. Use SQLite FTS5 as a rebuildable projection of titles, creators, abstracts, context, and legacy tags, with direct exact key/identifier lookup first. Write the projection in the same transaction as the source change. No PDF-content indexing is introduced.

**Rationale**: SQLite allows concurrent readers but serializes writers; transactions protect key allocation and stale-update checks, while filesystem operations need a separate protocol. FTS5 offers lexical retrieval without introducing a search service. Original imports as BLOBs simplify a consistent snapshot and full export. [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [Python sqlite3](https://docs.python.org/3/library/sqlite3.html), [FTS5](https://www.sqlite.org/fts5.html).

**Alternatives considered**: WAL remains an option if measured reader/writer contention justifies it. An external index is premature for the academic slice. Plain scans remain useful as a small reference implementation in capability-replacement validation, not a second production search system. SQL migrations are forward-only numbered resources with pre-migration backup and explicit `refs migrate`; opening a catalog does not silently upgrade it.

## R3. Bibliographic profile, parsing, and export fidelity

**Decision**: Use `refs-bibliography-v1`, an owned profile with a pinned Zotero vocabulary baseline, shared CSL concepts and typed native extensions. Do not adopt unmodified Zotero JSON, CSL-JSON, or BibLaTeX as the whole catalog. The [standards decision](../../docs/bibliographic-model.md), [mapping contract](contracts/bibliography.md), and [coverage inventory](contracts/bibliographic-coverage.json) provide the alternatives, exact source pins/hashes, paths, guarantees, and fixture obligations.

**Evidence**: Two research agents independently examined canonical-model alternatives and difficult mappings. Published schemas show many-to-one Zotero→CSL type mappings, distinct name particles, richer date roles, literal editions, multivolume title hierarchies, and publication lists. The existing narrow model did not account for those distinctions. The inventory enumerates all 40 Zotero types (37 bibliographic plus three supporting types), 45 CSL types/103 properties, and 51 explicitly declared BibLaTeX entry types with field groups. Vocabulary enumeration is performed design evidence, not adapter certification. [Zotero schema](https://github.com/zotero/zotero-schema), [CSL schema](https://github.com/citation-style-language/schema), [BibLaTeX datamodel](https://github.com/plk/biblatex/blob/v3.22/tex/latex/biblatex/blx-dm.def).

**Parser decision**: Keep `bibtexparser==2.0.1` as the provisional syntax adapter and `pylatexenc~=2.10` for explicit text/group parsing. Freeze raw parsing and duplicate/case-collision checks before transformations. The parser documentation does not certify full BibLaTeX/Biber behavior; neither package selection nor successful parsing proves semantic fidelity. Required fixtures cover names, protected groups, macro expressions, field datatypes, exact inheritance rules, edits invalidating old expressions, and the trial's real data. A blocking fixture failure requires a focused adapter/package reassessment before shipping. [Parser scope](https://bibtexparser.readthedocs.io/en/main/biber.html).

**Output scope**: Initial public output remains BibLaTeX and traditional BibTeX under explicit bounded profiles. CSL-JSON is an internal mapped validation representation, not a newly added public format. Quarto/Pandoc rendering checks target-specific title casing and protected text without rewriting catalog titles. BBT Extra directives are recognized and preserved with unsupported-application diagnostics until explicit field reconciliation; arbitrary raw directives/custom TeX are not silently passed through. Unknown custom fields and unsupported inheritance retain originals and visible limitations. [Pandoc bibliography handling](https://pandoc.org/MANUAL.html#specifying-bibliographic-data), [BBT Extra](https://retorque.re/zotero-better-bibtex/exporting/extra-fields/).

**Alternatives rejected**: A custom BibTeX grammar duplicates mature parsing work. Unmodified Zotero makes its current field ceiling ours; CSL-only storage loses native distinctions; BibLaTeX-only storage couples ordinary edits to processing syntax. Typed namespace fields supply usable structured extensions, while immutable raw evidence remains separate. One fact has one authoritative editable value, and every target mapping has its own loss/error report.

## R4. Initial Zotero route and partial imports

**Decision**: Implement an offline snapshot adapter accepting a consistent Zotero database, Better BibTeX key store, and manifest containing original library/storage/root locations and schema identifiers. Obtain that input while Zotero is closed, then open the supplied snapshots read-only. Detect required schema capabilities and reject unsupported layouts before applying records. Preserve source bytes, schema fingerprints, and adapter version. The published bibliographic vocabulary is not the SQLite schema contract: certify each separately. Import notes, attachment metadata, annotation records, and asserted source relationships into the structured supporting model defined by the bibliography contract; retain missing/unresolved parents and URL-only attachments. Read-only inspection/full export are required, while editing/rendering remain deferred. Normalize source identity as originating library identity plus item key, never numeric row IDs alone. Imported attachments remain linked to original locations, not temporary snapshot directories.

**Rationale**: The observed library includes pinned keys, many creator roles, hierarchical collections, annotations, and several attachment kinds. A `.bib` export alone is not sufficient migration evidence. Zotero documents closing the application before copying its data; the upstream schema provides the adapter's structural reference. [Zotero data guidance](https://www.zotero.org/support/zotero_data), [schema source](https://github.com/zotero/zotero/blob/main/resource/schema/userdata.sql).

**Partial application**: Retain a batch and one outcome per input entry, including malformed blocks. Commit each conflict-free source and its immediately available relationships independently. Retain conflicts and invalid entries for reconciliation. Resolve collection parents before children and defer relationships to unresolved sources. A repeated artifact from the same origin reuses entry identities and cannot duplicate applied work. An interrupted import resumes from retained entry state.

**Alternatives considered**: Zotero RDF is a broad export route; Better BibTeX JSON/JSON-RPC may reduce database-schema coupling. Neither is presumed to preserve the full required sample without testing. They remain fallback adapter choices, not additional initial integrations. [Zotero export guidance](https://www.zotero.org/support/kb/exporting), [Better BibTeX interface](https://retorque.re/zotero-better-bibtex/exporting/json-rpc/).

**Acceptance boundary**: Snapshot schema fixtures, representative PDF annotation usability, and the real-paper trial are implementation/release evidence, not completed planning research. The chosen route is explicit; the adapter must fail closed on an uncertified schema and cannot label an untested migration complete.

## R5. Deterministic name tokens

**Decision**: Use NFC normalization followed by Unidecode 1.4.0 with strict unknown-character handling, then refs-owned punctuation and case rules. Record policy `creator-unidecode-1.4.0-v1` and package version with generated keys. Original names and explicit overrides survive. Reject unsupported/control/symbol input and empty letter mappings rather than silently dropping them. A mapped token is a deterministic identifier fragment, not a verified linguistic romanization. Preview non-ASCII conversion and warn about language-independent mappings; the user can provide a preferred token.

**Rationale**: Synthetic wheel probes found useful coverage without runtime dependencies. Unidecode's wheel is 235,837 bytes (903,391 bytes unpacked); text-unidecode 1.3 is smaller but silently loses some unsupported input. Unidecode is GPLv2+; record that dependency license without implying a project license has been selected. [Unidecode documentation](https://github.com/avian2/unidecode), [release metadata](https://pypi.org/project/Unidecode/).

| Synthetic input | Executed result: NFC + Unidecode 1.4.0 strict | Design consequence |
| --- | --- | --- |
| `García`, including decomposed accent | `Garcia` | Normalize equivalent input before token generation. |
| `Łódź`, `Søren`, `Straße` | `Lodz`, `Soren`, `Strasse` | Accent stripping alone loses meaningful letters. |
| `Иванов`, `Παπαδόπουλος` | `Ivanov`, `Papadopoulos` | Useful tested Cyrillic/Greek coverage. |
| `山田` | `Shan Tian ` | Does not produce the Japanese reading Yamada; expose conversion and allow override. |
| `القرشي` | `lqrshy` | Available mapping need not match a person's preferred spelling. |
| `𠮷`, private-use `U+E000`, `😀` | Strict error | Require an explicit key/creator-token override. |

**Alternatives considered**: Stdlib normalization handles combining accents but is not general transliteration. text-unidecode 1.3 has a smaller footprint and different licensing options, but its unsupported-character behavior is weaker for this use. Language-specific romanization is deferred until actual names demonstrate that overrides are inadequate. [Unicode normalization](https://docs.python.org/3/library/unicodedata.html), [text-unidecode source](https://github.com/kmike/text-unidecode), [mapping change history](https://raw.githubusercontent.com/avian2/unidecode/master/ChangeLog).

**Validation**: Probe outputs are planning evidence from temporary synthetic inputs only. Add real sample names before migration acceptance. Pin policy behavior with regression cases for equivalent Unicode forms, ambiguous mappings, unsupported characters, overrides, and collisions. A package upgrade requires comparison; changed outputs require a new policy version and never regenerate assigned keys.

## R6. Files, export adoption, and crash recovery

**Decision**: Run filesystem work synchronously under a per-home advisory lock, coordinated with durable operation rows. Transfer regular files through exclusive sibling staging, verified content, no-overwrite publication, catalog-link commit, and source cleanup in that order. Use pathlib throughout, including `destination.hardlink_to(staged)` for atomic no-overwrite publication on tested local filesystems; this delegates to `os.link(staged, destination)`. Use `staged.replace(destination)` only for authorized replacement. Retain `os.fsync`, descriptor-level `os.open`, and fcntl where pathlib has no equivalent; fail safely when required primitives are unavailable. See the [API rationale](dependency-audit.md#pathlib-and-durable-publication). Keep the source until destination verification and catalog commit. Recovery examines actual fingerprints because a crash can occur between an effect and its recorded state. Initially decline relocation of unrecognized multi-file bundles or attributes whose preservation cannot be verified; linking remains supported under FR-034.

**Export decision**: Track adoption per canonical destination and last successful raw-byte digest. A new output is created without replacement. An unadopted existing output requires reconciliation and explicit adoption. An adopted output matching its previous digest can be replaced on explicit export; external changes require reconciliation or explicit overwrite. Stage and validate output, retain previous bytes for recovery, journal old/new digests, recheck, atomically replace, and only then advance the catalog baseline. Detailed states are in [file operations](contracts/files-and-recovery.md).

**Rationale**: Python supplies durable flush, no-overwrite link, atomic replacement, and advisory-lock primitives; none makes files and SQLite one atomic transaction. Plain move or overwrite calls do not satisfy the required recovery reporting. [Python os](https://docs.python.org/3/library/os.html), [advisory locks](https://docs.python.org/3/library/fcntl.html), [copy metadata limits](https://docs.python.org/3/library/shutil.html).

**Supported failure model**: Process interruption, ordinary I/O errors, and competing refs processes using one catalog home are covered on tested local filesystems. Source bytes must be readable and stable during transfer; external editors must not write the export destination during publication. A hash-check followed by replacement cannot provide compare-and-swap protection against arbitrary concurrent editors. Preserve prior output while unresolved and detect changes visible before publication. No claim covers hardware destruction, hostile filesystem replacement, or two independent catalog homes writing the same output. Materialized local cloud-sync folders can hold attachments, but concurrent outside content changes remain conflicts; the live catalog itself must be on local nonsynchronized storage. [SQLite atomic-commit assumptions](https://www.sqlite.org/atomiccommit.html).

**Alternatives considered**: WAL does not solve filesystem transactions. A background job system adds operational burden. Cross-volume rename fails, and an ordinary replacing rename can destroy an unrelated attachment. A universal multi-file transaction is outside the first slice; explicit recovery is the required guarantee.

## R7. Configuration, matching, mapping, and bounded defaults

**Decision**: Use the feature's documented A-02/A-03/A-04/A-05/A-06 defaults as planning selections without claiming they were independently approved in clarification. User preferences are TOML, with a small project whitelist, one discovered project file, visible origin for each setting, and explicit catalog-home selection. Collections map to safe relative paths beneath the library root, with per-collection overrides and reserved `Unfiled`. Exact names and grammar are in [configuration](contracts/configuration.md). Existing unsafe imported collection names remain catalog data and require a safe folder mapping only when used for managed placement.

**Identity decision**: An explicit catalog or origin identity is checked against all supplied identifiers; contradictory evidence never loses to precedence. Persistent identifiers are normalized by scheme, not by fuzzy title matching. Exact shared identifiers can identify a candidate, but incompatible editions/types or competing keys require reconciliation. A changed field is not automatically applied even when identity is clear. Preview decisions are rechecked at execution.

**Rationale**: These defaults make the draft executable without asking the user to design internals. They preserve the accepted separation of identity, filing, and project use. General folder sanitization, unrestricted configuration inheritance, and automatic duplicate merging are rejected because they can change meaning or destinations invisibly. A title-only or address-only source with no usable generated title words must supply an explicit key; this follows the existing explicit-override rule without inventing bibliographic facts.

## R8. Recovery bundles and leaving refs

**Decision**: Use a versioned directory backup bundle containing a consistent SQLite snapshot, preferences, a resource inventory, and a checksummed completion manifest. Original import bytes reside inside the snapshot. Acquire the filesystem coordination lock, refuse unresolved transfer/export operations, snapshot through the SQLite backup API, and derive inventory from the snapshot. External attachment contents, including managed attachments, remain excluded and explicitly listed. Restore into a newly claimed empty destination, validate members/schema/hashes/integrity, and publish a ready marker only after success.

**Full export**: A separate documented directory format contains UTF-8 JSON/JSONL for records and relationships, preferences, and raw original payloads keyed by digest. It is recoverable without understanding SQLite or installing refs. Restoring adopted export baselines marks them for revalidation before the next replacement, because files may have changed since backup.

**Alternatives considered**: ZIP adds extraction and path-validation concerns without initial user benefit. Copying only a live SQLite main file is unsafe. A project `.bib` cannot preserve the whole library. A raw SQL dump is not the user-facing exit format. [SQLite backup API](https://www.sqlite.org/backup.html), [corruption hazards](https://www.sqlite.org/howtocorrupt.html).

## R9. Capability boundaries and practical scale

**Decision**: Keep a small read-only `SearchProviderV1` boundary over a catalog-owned projection. Select built-in SQLite search by default; discover explicitly selected external implementations through `refs.search.v1` package entry points. Providers receive no catalog write capability. A small separately installed literal-search fixture demonstrates replacement on the same inputs and filters without core modifications. This is one capability boundary with a proof fixture, not a general plugin distribution system. Import/export adapters remain narrow application-owned interfaces; a second production provider is not required for every adapter. [Python entry-point discovery](https://docs.python.org/3/library/importlib.metadata.html).

**Operating targets**: Initial support is macOS and Linux with Python 3.14 and a local SQLite build providing FTS5. Plan for 10,000 sources, 30,000 resource links, and four concurrent CLI processes. On the documented reference development machine, warmed metadata search/list operations should meet p95 ≤1 second across 100 predetermined queries; measure installed-command overhead separately. File transfers have progress based on bytes, no fixed completion-time promise. These are new engineering validation targets, not claims about current performance or a delivery date. The observed 562-source library motivates headroom; horizontal scaling and Windows are excluded from the initial platform test matrix.

**Rationale**: The first feature needs dependable local behavior and affordable verification. Future QMD/Jev experiments remain deferred. Exact package build, schema capability, filesystem, and real-corpus acceptance are tested during implementation; the revised profile resolves the planning choice, while package compatibility, mapping fixtures and real-corpus fidelity remain required implementation gates. Task generation must include that work rather than treat the registry as passing interoperability evidence.
