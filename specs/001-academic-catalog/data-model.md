# Data Model: Academic Catalog Workflow

**Status**: Phase 1 design; no migrations have run. [Record contract](contracts/records.md) defines boundary types; [file protocol](contracts/files-and-recovery.md) defines durable external effects.

## Bibliographic standards profile

The [bibliographic contract](contracts/bibliography.md) defines shared fields, native type/field namespaces, independent coverage guarantees, and target projections. `metadata_json` stores profile ID, shared type plus native classifications, typed citation/native fields, richer titles/dates and publication arrays. Creators/identifiers remain relational and are assembled into the public record. There is one authoritative editable value per fact; immutable source expressions are evidence. Schema-profile pins are distinct from database schema version and are included in backup/full export.

## Shared Rules

All catalog-owned identities are UUID strings, stable across export/restore. UTC timestamps use ISO 8601 with a `Z` suffix. Revisions are positive integers beginning at 1; a successful changed mutation increments the affected aggregate once, and a no-op does not. SQLite foreign keys are enabled per connection. All persisted JSON is validated against the application model before storage. Identifiers and keys use binary uniqueness, not locale-dependent collation.

`catalog_meta` holds one `catalog_id`, schema version, application compatibility range, creation time, and catalog revision. Explicit migration validates version compatibility and creates a backup before changing schema. A read-only open never creates or migrates data. Preferences live in `config.toml`; recorded policy fingerprints explain prior results without becoming a second settings store.

## Metadata and Override Semantics

`metadata_json` excludes creators/identifiers stored in their ordered relational tables; the public source record assembles them without maintaining duplicate authorities. It contains type, title, optional main/subtitle/short/sort titles, language, dates, edition/version/variant, publication fields, legacy tags, and extension fields. The [record contract](contracts/records.md) enumerates types and clearing behavior. Every derived short/sort title records `mode=derived|explicit` and a policy fingerprint. A title correction recomputes derived values only. A preference change never eagerly rewrites stored values. Explicit normalize/rekey operations preview and apply selected changes.

Publication data includes distinct container/multivolume titles, ordered publishers/places/institutions/organizations, volume, issue, pages, article number, series and jurisdiction. Date roles include original/submitted/available dates and retain qualified precision. The authoritative edition statement can have a validated numeric interpretation. Source-specific recognized facts occupy registered typed namespaces, not only raw native fields. Preserve original TeX and protected spans separately from decoded searchable text; normalize only supported text. Original imported type/fields remain in the artifact and `native_fields`, even when output does not use them. Recognized native fields and citation fields are mutable through registered paths. Unknown user-supplied extension fields live under `extra`; unknown top-level input keys are errors to catch misspellings.

Creator token generation never participates in source-identity matching. A corporate alias affects a key only; it cannot manufacture a corporate author. A collision suffix changes only the new key. Explicit rekey frees the previous key after a preview warning; automatic alias retention is not promised in this slice, and no external manuscript is rewritten.

## Core Invariants

1. Every retained source has one stable ID and assigned key. If title/address metadata or a valid container-and-part description cannot produce a key under supported rules, creation requires an explicit key. Missing bibliographic facts remain missing.
2. Every applied import entry identifies its retained entity/entities and saved fingerprint; a standalone supporting item need not have a source. every input block has an outcome. Entry processing and its entity/relationship changes commit together. Unresolved dependent relationships stay listed as unresolved, never silently dropped.
3. Filing reassignment updates an intended collection but not the recorded current location. The reorganization preview compares current path with the derived destination. `Unfiled` allows intake before a filing choice.
4. A resource can be `managed` while its current path is outside the library root after explicit adoption. It remains there until reorganization. Managed means authorized filing behavior, not proof it has already moved.
5. Resource/target reservations in active file operations are checked by source removal, unlink, rekey where relevant, and reorganization. Conflicts return `operation_in_progress`; no dangling journal references are permitted.
6. An export baseline advances only after complete publication, or recovery that verifies the recorded new digest. A failed command cannot claim a successful baseline.
7. Source removal marks the source `removed` and deletes active relationships/search projection in one transaction after preview/confirmation, retains the source row and necessary import/provenance evidence for valid foreign keys and replay, and touches no external files. Removed resources remain in historical inventory with their original locators and are excluded from ordinary listing; no external bytes are deleted. A later replay returns its historical outcome with `source_removed` rather than recreating it implicitly. Reimport of the same origin requires an explicit create-distinct reconciliation to bind a new active source; preserve the earlier origin binding as provenance. Removed-source keys remain reserved to avoid reusing a key still present in older writing. Full logical export includes tombstones with their state; this is not a general undo interface.
8. Canonical output paths resolve the parent directory and basename; output symlinks are rejected. Managed path components cannot escape the chosen root through `..`, symlink traversal, or absolute overrides. Link-in-place supports existing files without taking ownership.

## State Transitions and Concurrency

| Aggregate | States | Rule |
| --- | --- | --- |
| Import batch | `processing`, `complete`, `partial`, `failed`, `interrupted` | Complete means every entry applied/unchanged; partial has retained conflict/invalid outcomes; interrupted has pending work. Counts include every entry. |
| Regular-file transfer | `prepared`, `staged`, `published`, `catalog_committed`, `cleanup_pending`, `complete`, `conflict`, `recovery_needed` | The published destination is verified before catalog update; a move's source is removed only after that update and fresh source checks. Copy ends without source removal. |
| Export | `prepared`, `staged`, `published`, `baseline_committed`, `complete`, `conflict`, `recovery_needed` | Record previous and candidate bytes/digests before publication. Recover by comparing actual target bytes, never by trusting a stale stage alone. |
| Restore destination | `initializing`, `ready`, `failed` | No ordinary command can open an incomplete restore as a usable catalog. Completion includes schema and integrity verification. |

Use `BEGIN IMMEDIATE` for writes with a five-second busy timeout. Conditional revision updates must affect exactly one row. Hold no database write transaction while copying bytes or invoking an external opener. A per-home `flock` coordinates filesystem operations, backup, and recovery; the lock file is created by setup and never replaced while in use. Ordinary metadata edits use database concurrency; reserved-resource operations are protected by explicit reservation checks.

Readers use one consistent snapshot per result/export. Changing metadata during export does not invalidate the snapshot; output identifies the selection/config fingerprint it used. A newer catalog state appears in the next explicit export. Resource removal and export-target rebinding during an active file operation are rejected.

## Backup and Schema Evolution

Backups include the consistent database, user preference bytes, and a resource inventory with hashes for bundle members. External file contents are explicitly excluded. Restore preserves catalog identity and source IDs, but revalidates export adoption against current filesystem state. Only one actively mutating home for the restored catalog is supported when they reference shared files.

Schema migrations are monotonic and explicit. Unknown newer schemas are refused; known older versions can be upgraded with a backup, transaction, and verification. Full logical export has an independent format version and includes ordered relationship records plus original artifacts, so migration away does not require executing the schema. See [interchange](contracts/interchange.md).
