## Technical choices

These are **implementation proposals**, not additional owner quotations. Python >=3.14,<3.15; Typer >=0.27.2,<0.28; Pydantic >=2.13,<3; bibtexparser==2.0.1 as a guarded block adapter; pylatexenc==2.11 for supported one-way text decoding. Four runtime dependencies, no network/model service or transliteration dependency. Use stdlib SQLite, TOML, pathlib, hashlib, unicodedata and narrowly justified descriptor/platform calls. No ORM or generic repository hierarchy.

Use uv_build >=0.12.1,<0.13, committed uv.lock, exclude-newer="3 days", and uv sync --locked. pytest/pytest-cov and Ruff are development tools; pin the evaluated ty version when creating the environment. These selections retain the prior research; no new dependency evaluation is implied by the trim.

SQLite rollback journal, foreign keys, synchronous FULL and short BEGIN IMMEDIATE writes protect revisions and key allocation. A five-second busy timeout produces an actionable retry result. Slice 1 has ten logical tables including one FTS projection; SQLite's internal FTS shadow tables are not additional domain tables. Config stays separate from cat/lib. macOS is first; Linux support requires the same affected contract checks.

## Structure and capability boundary

Keep ordinary modules for CLI, validated records, catalog/configuration, naming, bibliography, files and snapshot recovery, with Bib/CSL adapters. Domain functions use refs-owned values/errors, independent of Typer and SQLite row types. File adapters own only the platform primitives needed for verified copy and publication. A plain migration runner owns schema changes; catalog open upgrades supported older schemas automatically after a dated safety copy (owner decision, 2026-09-23: "normally it is handled automagically"; "agree with A").

The internal read-only search boundary takes literal query/filter/limit/offset and returns source IDs, revisions, matching fields and ranked snippets/availability. The application resolves authoritative records and enforces catalog policy. SQLite FTS5 is its only implementation. Rebuild the derived projection from authoritative values as needed internally; there is no index rebuild command. No entry-point selector, provider schema or proof package ships. Constitution IV/V require selection and replacement proof when a second implementation is evaluated, not now.

## Slice 3 brief: organize files

Owner direction, 2026-09-22: after the ingest, "clean it up / reorg the refs folder, and migrate other adhoc papers / bib consumers to the new method." Earlier (2026-09-21) the PDFs were to move to a visible folder on Casa, renamed and cleaned up, and synced to other devices with Syncthing. This is the destructive slice: the move-with-delete protocol gets full specification, an experiment on a copy of the real tree, and an independent review before it touches the library. Everything else in the slice is decided by use.

### Outcome

Every file the catalog knows sits under `/Volumes/Casa/refs/lib`, recorded by root and relative path, in a folder tree that is its filing. The old Box tree and the Zotero storage folder hold nothing refs owns. New intake from Downloads moves the file rather than copying it. A file can be refiled by an explicit, previewed move. An interrupted move can be re-run to completion with nothing lost and nothing duplicated. Syncthing shares lib with the owner's other devices; that is a Syncthing setting made after the move, not a refs feature.

### Observed inputs, read-only, 2026-09-23

551 catalog resources, all absolute links, none under a named root: 511 under `~/Box Sync/zotero` (4.2 GB, all PDF) and 40 under `~/Zotero/storage` (37 HTML snapshots, 2 JPG, 1 PDF). Every linked path resolves. The Box tree has 517 real files: the 511 plus six PDFs no source links (two copies of Boost Your Git DX, ZeroToSoldMobile, Thomas 2025, ExploringMITCurricwithLLM, Bailenson). Zotero storage has three more unlinked PDFs. ### Decisions, 2026-09-23

D1 Layout. Proposed: keep the collection tree, moved intact, with the folder under lib as the filing collection. The owner reframed it: "I never liked Zotero's collections mechanism and the fact that a ref can be in more than one ... projects ... replace collections ... a separate field ... should determine folder structure - folders are for topics, projects are for citations ... start with the current structure under box sync, but I would intend to rework it soon thereafter". Decision: a refs-owned field `loc` on the source, one value, a relative path such as `dissertation/mixed-reality`; every file of the source lives under `lib/<loc>`; absent, not placed (D5). Owner: "a source (bib entry) can refer to several files, but will have only one loc, and all files will go there"; "for the initial move we'll populate loc with the relative path from box sync root"; "let's just call it location or loc, I prefer the short-form". The supplied rehearsal sample has 510 sources with files and 65 without. Initial assignment follows D5; collections are not placement evidence. Loc paths are stored NFC and compared case-insensitively, with no leading slash or parent segments. Collections become import history; the tables and `--collection` filter stay until unused.

D2 Names. Decision A: the move preserves names. Owner: "I agree with A"; on bulk rename, "not no, deferred", to be wired in "as an optional part of the reorg process" once rename is implemented and tested. Evidence: the convention applied to the 553 existing files would give 201 names over 60 characters and seven within-source collisions, since imported files carry no labels; 243 records with a short title come out well.

D3 Unlinked files. Owner, on the copied originals left in the Box tree: "I don't mind the extras in the Box folder. it is essentially an archive / backup of zotero db for now." Unlinked files stay where they are and the move report lists them.

D4 Intake default. Decision A: `add --file` moves the file by default, copying into `lib/<loc>` of the source, verifying, then deleting the original; `--copy` keeps the original; `--link` links in place. `resource add` keeps linking in place as its default, because attaching a file that already sits where it belongs is its ordinary use, and gains `--move` beside the existing `--copy` (clarified 2026-09-23 on the authoring session's question). Owner: "I think move should be the default". No exception for a file already inside lib: "you can't reorg something before it is added, so add moves it to the source loc. you can reorg it later if wanted". For move intake, a file already recorded as a resource of any source is refused, naming that resource: "I would probably block this. it seems unlikely that it would be intentional. if so we can fix it later."

D5 Linked files and reorg, from the protocol review. Owner: "loc can be empty, eg when linked. files with an empty loc field would remain linked and unaffected by reorg. if you want to convert a linked file to managed, set the loc field and run reorg". Decision: loc is optional; empty means not placed, and reorg ignores the source's files. Move intake writes `unfiled` explicitly when no `--loc` is given; `--link` intake leaves loc empty. This replaces the earlier wording that an absent loc means unfiled. The cutover is: assign locs to every source with a file, then run reorg. File-less sources keep an empty loc. Initial assignment now uses the Box-tree folder, otherwise the managed-file folder relative to the library root, otherwise unfiled for non-topic storage such as Zotero item-key folders. Collections never determine loc. Owner: the collection fallback "conflates the collection (typically used for generating bibs for papers / pubs) and location, which is exactly what we were trying to avoid". Owner: "use 'unfiled' as the folder name. all lower case."

D6 Colliding preserved names, from the protocol review. Owner: "handle this in the same way we do keys now, by adding an a, b, c... to the end of the filename and recording the duplication; we can do something fancier after / during the rename work." Decision: when a preserved name would collide in the destination folder, the first file keeps its name and later ones take `-b`, `-c` before the extension; the operation row and the report record old and new names. The intake convention's no-suffix rule is unchanged.

### What is built, proposal

1. One move protocol, used by every route: copy to `cat/staging` with an exclusive name, fsync, atomic publish into lib without overwrite, verify the destination digest against the source digest, then in one transaction re-record the resource as root plus relative path and mark the original as pending removal, then delete the original and mark the operation complete. Filenames are written NFC. A `file_operations` table (one row per file: resource, source path, destination, digest, state, timestamps) is the journal; re-running the same command resumes from the recorded state. No request-ID replay, no operations list/show, no native metadata adapter; `resource check` reports incomplete operations and files whose folder disagrees with their source's loc, and the report of a completed move lists every old path beside its new one, which is what the vault link fix needs.
2. `loc` on the source: set at `add --loc`, changed or cleared with `update`, shown by `show`, filtered by `list --loc` and `search --loc`. Changing loc never moves a file. The initial assignment is a one-time step of the cutover for every source with a file: the folder of its Box-tree file, else its managed-file folder, else unfiled for non-topic storage (D5), previewed and reported before any move.
3. `reorg`: previewed move of every file whose folder disagrees with its source's loc, optionally scoped to one source or one loc prefix. The 551-file cutover is `reorg` run once after the initial loc assignment, with lib empty; later reworks are the same command. Renaming joins it later as an option once implemented and tested (D2).
4. Intake by move per D4, through the same protocol, into `lib/<loc>`.
5. The sync setup is a Syncthing folder added by the owner after the move; refs records nothing about it. `resource check` already recognizes sync-conflict filenames.

Budget: about three invocations plus the `--loc` options, one column and one table, no new dependency, roughly 700 source lines. Score should hold at 6. Journals, recover commands, request-ID replay, forced directory syncing beyond the fsyncs above, and the native metadata adapter stay deferred until an interruption in real use shows what re-running does not cover.

### What must never break

No delete before a verified copy; no overwrite in lib. The owner runs a CCC backup covering Box and Zotero storage before the bulk move: "I'll just run a CCC backup before we actually run slice 3". Existing filenames, citation keys, the Zotero database and the vault remain unchanged. The owner repairs vault references from the report. The never-cut list in `AGENTS.md` applies.

### Acceptance gate

Rehearse in a temporary home on copied catalog and files: a clean run, interruption between publish and re-record, and interruption between re-record and delete. Re-runs complete with matching digests, no missing files and no duplicate resources. The owner-authorized cutover then moves the 551 resources, followed by resource check, sample opens and manual vault repairs.

### Process

Independently review the [move protocol](contracts/files-and-recovery.md#move-protocol-and-journal) before tasks. Then build against synthetic fixtures, rehearse on copies and obtain owner authorization for the real move.

Decisions were made on 2026-09-24 with the owner's words: "you will honestly answer this better than I will because you know, or can determine, what is necessary / desirable in those situations. debate and recommend", and at the end "ok with json lines and stdlib plus rich".

### Outcome

One log stream per catalog, at `cat/refs.log`, JSON lines, one object per line, never rotated. Levels from debug to error carry what the tool did; the lines written when refs changes something are complete enough to reverse the change, reach the disk before the change takes effect, and are never discarded. The terminal stays the report; the file is the record.

### Decisions

D1 What is recorded. Every command writes an opening line and a closing line with the outcome and exit code, so a run reads as a bracket. Reads and previews write those and nothing else. A mutation writes one line carrying the fields that make it reversible: the target by id and citation key, resource id or batch id; the revision before and after; and `changes`, a map of changed paths to old and new values for metadata, or old path, new path and digest for a file, or counts for a batch. The reason full values are recorded: the database keeps the current record and the preserved original, not intermediate states, so these lines are the only per-change history refs has; an agent rewriting forty records on a Tuesday is answered by the log, not by Monday's backup. What never appears: file contents, the preserved original bytes, and anything from configuration that is not a path. Debug tracing (files hashed, statements run, timings) is off unless asked for per invocation.

D2 One file, never rotated. A year of the owner's use is a few megabytes. The requirement that mutation lines reach the disk and are never lost is met inside one file by one handler that flushes and fsyncs when the line is a mutation and not otherwise. The file lives beside the catalog because that is the folder that must never be synced. If a mutation line cannot be written, the mutation is refused with exit 5, the same rule as the schema safety copy: a change that cannot be recorded is not made. A failure to write chatter warns once on stderr and continues.

D3 Shape. JSON lines. Every line: UTC timestamp, level, an event name from a fixed set (`source.create`, `source.update`, `source.remove`, `resource.move`, `import.entry`, `export.write` and the rest), the command as invoked with its catalog path, the process id. The event names are a registry. Every mutating command emits at least one mutation event, and one test asserts it, so a new command cannot forget to log; an import emits one `import.entry` event per applied entry plus batch open and close events, and a move emits one `resource.move` event per state transition, with those counts asserted in the per-kind tests.

D4 Library. The standard library with a JSON formatter of refs's own, about twenty lines, and a context-variable filter that binds the command and catalog to every line; Rich's handler for the console, on only with `--verbose`, at debug, to stderr. No new runtime dependency: structlog's binding is fifteen lines here and would be the fifth dependency; loguru's conveniences do not include the one behaviour that matters, the fsync on mutation, which is a handler refs writes either way.

### What is built

1. `refs/logging.py`: the formatter, the filter, the handler with level-aware fsync, the event registry, and one `log_mutation(event, target, before, after)` call used by every mutating path.
2. The calls at each mutation site, placed before the effect: sources, resources, moves, importing, bibliography, projects, recovery.
3. `--verbose` on the root command; the closing line in `results.emit`.
4. Tests per the convention: the coverage test over the event registry; one test per mutation kind comparing the log line with the database state after; the refusal when the log cannot be written; the piped and verbose console behaviour. Every test in a temporary catalog.

### What must never break

The result envelope. The move protocol's ordering: the log line precedes the effect, and the fsync of the line precedes the deletion of an original. No log line ever contains file contents or original bytes. The never-cut list in `AGENTS.md`.

### Process

The light loop. This queues behind the human-output pass, which restructures `results.emit`; it is small, about 200 source lines, and it goes to the authoring session in its own worktree after that pass merges. Governing text stays net-flat.

## Types and kinds brief: ask refs for podcasts

Owner direction, from the round three census on 2026-09-25 and 2026-09-26. On the refusals: "shouldn't we be using these refusals as evidence that a parent item type needs to be added?" On what admitting means: "we would essentially create a schema that is specific to refs, a superset of the others, and a mapping to those ... correct?", answered that the canonical vocabulary is CSL's and admitting a type switches on a CSL type with its mappings. On proceedings: "could we have proceedings use the book CSL type but override that locally with `proceedings`?" On deferred types: "where anticipated refusals happen, i.e., where we defer legal family until an example import hits, we should announce that with a recommendation to add the type." On the vocabulary: "I don't want to have to remember that podcasts are internally labeled song, because that is dumb but the best csl allows. I want to refer to them by a more meaningful name. I don't want to have to think about other internal representations or how any of that should be correctly translated to any consumer schema. I just want to ask refs for podcasts and get the right stuff"; and "perhaps refs should announce when something is added to a category in which aliases exist and enumerate those?" On the revision guard: "`--if-revision 3` ... feels a bit too fidgety for human users." The recommendations below were accepted with "proceed as described" on 2026-09-26.

### Outcome

Eight more CSL types are admitted, five more spellings map onto types refs already has, and every other kind the census found refuses by name and says which CSL type would admit it. A kind is a name the owner uses, defined as a rule over the record, so `refs list --kind podcast` returns podcasts and nobody types the word song. The revision guard on `update` becomes optional for people and stays available for agents.

### Decisions

D1 Admitted types. `periodical`, `entry-encyclopedia`, `map`, `graphic`, `motion_picture`, `song`, `broadcast`, `dataset` and `post`, each with its Zotero and BibLaTeX spellings on import, its field applicability, and a portable projection. Plain BibTeX has none of these, so the projection is `@misc` carrying the canonical type and genre in fields that survive a round trip: export then import yields the same canonical type and genre, and one test per type proves it. A BibLaTeX profile that emits the native entry types is deferred until a consumer needs it.

D2 Mappings onto existing types. BibLaTeX `proceedings` and `collection` to `book`; `booklet` and CSL `pamphlet` to `document`; `generic` to `document`; `presentation` and `talk` to `speech`; `softwareversion` to `software`; Zotero `forumPost` to `post`. The native label already stored on every imported source refines export the way it does for theses: a `book` whose native label is `proceedings` exports as `@proceedings`, and the same for any native label that is a valid entry type in the portable profile. Human output shows the native label beside the type when one exists.

D3 Deferred types announce themselves. The registry lists the CSL types refs knows and has not admitted (`legislation`, `legal_case`, `bill`, `regulation`, `treaty`, `hearing`, `personal_communication`, `review-book`, `musical_score`, `performance`) with their route spellings. A refusal for one keeps its code and adds the CSL type and one sentence recommending admission by a type row. `nameonly` and `hardware` refuse as before with no recommendation, since CSL has no type for them.

D4 Kinds. A kind is a registry row: a name, a canonical type, and the field values that define it, read from metadata and written by setting metadata, never stored as a fact of its own. The first kinds: `podcast` is `song` with genre "Audio podcast"; `lecture` is `motion_picture` with genre "Lecture recording"; `talk` is `speech` with genre "Conference presentation"; `proceedings` is `book` with the native label `proceedings`; `dataset` is the type `dataset`. The genre wording is the registry row's and changes without code. A record has one kind, because it has one type and one genre.

D5 Assignment. Import assigns a kind when the origin determines it: a Zotero podcast is a podcast. Where a type has kinds and none is determined, the entry carries a warning naming them, in the dry run and in the import record. `add --kind` and `update --kind` set the defining fields; setting a kind on a record whose defining field holds a different value refuses and shows both values, as import conflicts are shown. `list --kind` and `search --kind` filter; `--kind unassigned` lists sources whose type has kinds and none set. `refs kinds` prints the table.

D6 The revision guard. `--if-revision` on `update` is optional. Omitted, the update applies to the current revision and the result reports the new one; given, it behaves as now. Agents keep passing it. One sentence changes in the records contract.

D7 Authority, stated once. The registry is the authority for admission, spellings, field applicability, kinds and deferred types, and the importers read it. The exporter's per-type projection remains code, as D3 of the fix pass decided; each admitted type adds its branch beside a registry row that documents the projection. The structured projection column stays a later pass.

### What is built

1. Registry rows for D1 to D4, and the model's type literal generated from the registry so the two lists cannot disagree.
2. The exporter branches for the nine types and the native-label refinement, with the round-trip test per type.
3. The refusal detail and sentence for deferred types.

5. The optional guard on update.
6. Tests per the convention: admission and refusal by name per type and per route; the round trips; the kind rules including the conflict refusal and the unassigned listing; the warning's presence in dry run and record; the guard omitted and given.

### What must never break

The export of every existing entry, byte-identical, proven by the export test over the owner's catalog. The result envelope. Import never guessing a type or a kind it was not told. The never-cut list in `AGENTS.md`. No new table; one new command, `kinds`; no new runtime dependency.
