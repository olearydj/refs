# Converting a project to refs

How an existing writing project moves its bibliography into the catalog and takes its reference list back as an export. It began with the family-document pilot and is revised after each conversion; the findings at the end keep one short entry per project. Governing rules are in the contracts; this page is the working order.

## When a project qualifies

It has a bibliography file it builds from, kept by hand or by an agent, and the file is not an export from Zotero already in the catalog. The inventory review lists the candidates. A project in the middle of a submission still qualifies, because nothing here changes the project until the export is proven identical in meaning.

## The order

The order has two halves and a stop between them. The first half is read-only and ends in a proposal; nothing in the catalog or the project changes until the owner approves it. The second half executes the approved proposal and stops again only at the export gate. This is so the retypes, versions, unlinks and attachments are decided once, before anything runs, rather than discovered after a gate and redone.

### Propose, read-only

1. **Inventory the project.** Name every bibliography file, who writes it, and every consumer: a Quarto or pandoc build, a LaTeX build with biber or natbib, a venue that demands a `.bib`, a site build, a sync script. Say whether each document is published, delivered to someone, or internal, since that decides which version of a source it cites (see the rules below). Note the citation-key style; keys stay as assigned. Record which entries the prose cites, skipping Quarto cross-references such as `@sec-` and anything in code, and confirm the list against the rendered reference list. List the project's uncommitted and untracked files and any agent files it keeps out of git; the owner commits the work first or names it as left alone, and every later commit stages by path.

2. **Find the sources.** Read-only in this half: search the stores listed in the attach step below, match by DOI first and then by title, and list what was found with paths, what needs a fetch with the link, and what is URL-only. Check that each fetch link reaches the cited edition, by the venue line on the PDF where one is shown. Hosts that refuse scripted downloads go straight onto the owner's fetch list, so the owner can fetch them during execution. Nothing is downloaded or moved yet.

3. **Plan the records.** Check every entry against its source before planning it: an agent-written bibliography can carry an invented title, author list or venue, as two of dema-llm's entries did. A claim the prose makes that its source does not support is a finding for the project, fixed there on the owner's direction. From the bibliography and the sources found, decide per record what the completion step will do: the type the thing is, the kind, protected names, the software version and release date from the rule below, which notes move to context, and what file will be attached from where. For each preprint, decide which version each document cites; revisions of one preprint are one record, with the cited revision in context. Records the conversion creates take refs's key convention. A standard or regulation is cited by the version the text relies on. Decide one export target per profile the consumers need. Where one document's formats use different citation engines, ask the owner whether to standardize; a fact a style drops is fixed in the project's own copy of the style, not in refs. Predict the gate from records passed through refs's own admission (a dry run) and exported by the current profile, and from a full render of each consumer's output, including numbering and in-text links: identical, or changed with the expected wording.

4. **Stop for approval.** Write the proposal in the report template's first sections: backup name, inventory and consumers, planned import, planned record completions by key, sources found and the fetch list, planned targets and the expected gate outcomes. The owner approves, amends or declines. Only an approved proposal proceeds; an amended one is rewritten and approved again.

### Execute the approved proposal

5. **Backup.** `refs backup --output /Volumes/Casa/refs-backups/<date>-before-<project>-<pass>`, one per pass of a project, named by the pass. Check the manifest validates.

6. **Import.** `refs import --format bib --input references.bib` (or `--format csljson`) with the project named as origin. Read every outcome: applied is new, unchanged is already there, conflict means the catalog holds a different value for a bound source and both are kept for `import reconcile`, invalid names a limit and preserves the entry. Nothing is guessed; a refusal is recorded, not worked around.

7. **Create and cite the project.** `refs project create <name>` and `refs project cite <name> KEY` for every entry the prose cites, plus the ones the bibliography carries uncited if the owner wants them kept. The export is cited-only, so this list is the reference list.

8. **Complete the records** exactly as approved: One pass over every record before any export gate, so the gate runs once. Is the type what the thing is: a software project cited by its repository is `software`, not `webpage`; documentation is a `webpage` with the site as container title; a scanned order is a `document`. Does a kind apply: `repository` for source code repositories, `podcast`, `lecture` and the rest as the registry lists them. Are software and product names protected in the title, so styles do not recapitalize them. Refs title-cases English titles unless a record preserves its case, so the proposal decides the project's case policy once: title case for academic bibliographies and internal documents, preserve for archival material whose titles are sentence-case by nature, set by `[titles] policy = "preserve"` in `.refs.toml`. A style that recases titles is left to do so; in the owner's words (2026-09-27), "I strongly prefer title case for internal use. if IEEE, APA, Chicago want to mutilate that, so be it." For software, version and date follow the rule below. Notes hold facts meant for the page. Context holds only facts about the work and caveats needed to read the record correctly, such as a printed byline that differs or a version choice; never correspondence details, people not credited on the work, pointers to working notes or loosely related material, or process narrative, and never an association the work itself does not state (owner, 2026-09-28: "make a note not to overstep on context"). When in doubt, leave it out, or ask.

9. **Attach the sources** exactly as approved. Every record should end up connected to the thing it describes. Look first in the project folder and its figures, the vault project if there is one, the library at `/Volumes/Casa/refs/lib`, then DEVONthink exports and `~/Downloads`; for the owner's own works, the `pub` tree, the presentation folders, the CV's bibliography and the mail archive. Match by DOI first, then by title. Then by kind of source: an article is fetched by DOI, and open-access publishers have stable PDF locations (JOSE and JOSS by DOI path, PLoS by article id, DOI content negotiation where offered); paywalled and bot-gated hosts refuse scripted downloads as a rule and are a browser download by the owner through the university VPN: Elsevier, ACM, IEEE Xplore, Springer, OpenReview, the bepress repositories and government sites among them. Facts the owner supplies go into context with origin `user`. A software record gets the README at the default branch's current commit and the repository's API metadata, both named with the commit and the date. A web page gets one capture file: the page as served, or for a page that is only a script shell the content it loads, with its URL, retrieval time and hash; a JSON wrapper holding these is fine. A record keeps the accessed date its bibliography gives, since that is the reading the text reports; a capture made later records its own date in the resource and context, and without a given date the capture's date becomes the accessed date. Files move into the library by `resource add --move`, which names them by the convention and files them under `unfiled` until the loc taxonomy exists; a project's own raw material, such as a vault's scans, stays where it is and is linked in place with loc empty. A source with a scan and a transcription gets two resources with labels, given by `--label` on `add` or `resource add`; a label is a short tag, one or two words, hyphenated, such as `scan`, `capture` or `r2023-06-03`, since it also ends the file's name. The owner's fetches from the approved list are attached the same way; the pass is not complete until every item on the list is attached or disclosed as missing.

10. **Export per consumer, to scratch.** Add the project's register row on the execution branch before the first run. Changes that happen only at adoption, such as switched citation keys, a changed engine or a style edit, are applied to the scratch copy by a named preparation step in the row, removed after adoption. Run `uv run --locked python tests/fixtures/real-trial/conversion_check.py --project <registered-name>`; it reads the register, takes a read-only catalog snapshot, exports through refs into a scratch project copy, runs every consumer, and writes `gate.json` and `gate.md`. Each consumer is rendered by the venue's own pipeline where it runs locally, else by the closest local equivalent, named in the register row so the difference is a known gap; a bibliography gate is valid through the equivalent, since citeproc's reference list does not depend on the venue's layout, while a layout check is not. Never export over the project's file. A pandoc or Quarto consumer takes `--profile csl-json-v1`, the identity mapping; a Pandoc/biber consumer requiring a `.bib` can take `--profile biblatex-v1`, while a classic BibTeX consumer takes `--profile portable-bibtex-v1`. CSL JSON titles may carry CSL's own markup, `nocase` spans for protected case and the `i`, `b`, `sup`, `sub` and `sc` tags; citeproc renders them, and any consumer that formats titles itself from the export, such as a site build, must render or strip them too. Render the project from the scratch export with its own configuration and diff its reference list against the current render, entry by entry. The gate has three outcomes: identical; wording changed by a deliberate type or field correction from step 8, listed per entry with the exact before and after; or a fact lost or altered, which stops the pass until the record or a refs limit explains it. The owner decides adoption once, from the per-entry list. A gate that matches the proposal entry for entry is accepted without discussion; a mismatch in either direction is a finding.

11. **Adopt.** Only after the owner accepts the gate, rerun the same harness command with `--record` to save the current per-consumer fixtures and tool versions. Then export to the project's path, set the bibliography in the build configuration (per format when consumers need different profiles), write `.refs.toml` with the project and one `[[export.targets]]` entry per profile its consumers need, and commit those together, separately from any content change. Discovery of `.refs.toml` stops at the nearest git root, so a target inside a nested worktree is written from the publication folder, or from inside the worktree with `--project-file` naming the publication's config. The [files contract](../specs/001-academic-catalog/contracts/files-and-recovery.md) governs adoption and overwrites: a legacy file is adopted only if its bytes were imported in step 6, and an export later discarded through git needs `--overwrite` once the file on disk is confirmed; replaced bytes are kept as originals. When the gate passes, the exported file and the rendered reference-list text become that project's fixture, and its register row gains the refs version and the pandoc and Quarto versions it was verified against. After the adoption commit, run the check for the project again without `--record`; if every entry is identical, record again with the owner's quoted approval, so the register names the adoption commit.

12. **Retire the hand-kept file** once nothing reads it, in the same commit as the reader's switch, never before. When a generated target replaces the hand-kept file at the same path, adopt it in place; nothing is retired. Run the conversion harness for that project again after changing a reader; a gate alone is not authorization to retire another consumer's input.

13. **Document in the project.** A short `docs/refs.md` in the project: the catalog is the master, the export is generated and never edited, how to add and cite a source, how to re-export, and the checks after every export. Point to it from the project's README and its tracked agent instructions; agent files the project keeps out of git are edited in place, never committed.

14. **Report and record.** Write the pass report in the template below, add the findings to this page, and complete the register row. Feature decisions go to the plan's ledger, not to this page.

## Rules the steps rely on

A published work keeps the references it was published with. In the owner's words (2026-09-27): "we should never retroacively change a ref in one of my published works without specific direction to do that (e.g. my dissertation updates)". Internal documents go the other way: "the closer to the latter (internal) the more strongly I recommend switching from preprints to the published versions." A delivered version of a document still in use is found where it was delivered, usually the owner's mail. Before its references change, its exact file is committed beside the source (force-added if ignored), with a README giving recipients, date, hash and the nearest tag, saying so when the tag was made after the build.

A preprint and its published version are two records, each keeping the key it was first given and its own file, joined by `refs update --link`. A document switching to the published version changes its citation key at adoption; the preprint stays in the catalog for anything else that cites it.

A record links only the source's own file: its PDF, its capture, its scan. A project's synthesis or review note is a project document; a fact from it about one source goes into that record's context.

Each profile a project's consumers need gets one refs target; consumers that read the same profile share it. A script that copies one consumer's bibliography to another is the thing the targets replace; it keeps whatever manuscript projection it does and gives up the copy and any byte-equality check on it.

A software record's version is the release current on the record's accessed date, and its issued date is that release's date, both from PyPI or GitHub release history and recorded as a lookup in context, never guessed. Without them Chicago prints "released." with nothing after it.

## After conversion: adding a source

A converted project adds sources through the catalog, never by editing the export. The sequence is the conversion's execution half in small, without a backup for a single added source (owner, 2026-09-28: "I don't think one-offs need backups at this point"): the record added as refs JSON with the project's case policy, its file linked or copied and labelled as the project does, and its capture note in context; the key cited in the project; `refs export` with no arguments; the gate run without recording; its diff read, expecting only the new entries and any renumbering; then the record run from a clean tree at a commit, committed on a branch for the review session to merge. A project's own `docs/refs.md` points here and adds only what is particular to that project.

## Report template

Every pass report uses the same headings, so reports diff against each other: backup and scope; inventory and consumers; import outcomes by key; record completions by key; sources found, fetched, and the fetch list for the owner; attachments with final names and hashes; the export gate table with exact before and after per changed entry; commits; timing; findings in two lists, for refs, which become candidate changes in the plan's ledger, and for this guide, which become edits to it. The maintenance sequence above ends with the same two lists. Session reports live under `specs/001-academic-catalog/reviews/` named `<date>-<project>-<pass>.md`.

## Checks

The catalog backup validates; the import's counts sum to the file's entry count and every invalid entry has a named reason; the project's cited count equals the reference list the prose needs; the refs test suite passes after the import, since some tests read the live catalog; each linked or copied file's hash matches the original; the rendered reference list from the scratch export loses no fact; the build passes after the switch; the project's docs name the export and the re-export command.

After any change in refs to an export profile or a projection, every project in the register is re-exported from the real catalog read-only, re-rendered by every consumer in its row, the style and any hand-rolled formatter alike, and each reference-list text diffed against the last verified render; every difference is listed and explained before the change merges. A difference has two possible causes and the walk cannot tell them apart: refs changed what it exports, or the project changed what it cites. When a project's own content changes its reference list, the session that made the change re-runs the harness for that project and records the accepted render with `--record`, so the fixture follows the project and the next refs change is measured against the current list. Recording is always the second run: the gate runs first without `--record`, its diff is read, and the record run follows from a clean project tree at a commit, naming with `--work` a directory that does not exist yet. The suite tests refs's reading of its own exports and the corpus never renders, so the register is the only check that sees what a style prints. Run `uv run --locked python tests/fixtures/real-trial/conversion_check.py --all` for this walk. The [harness README](../tests/fixtures/real-trial/README.md) gives its outcomes, exit codes, extraction rules and what a project copy includes.

## Boundaries

Prose changes only on the owner's direction, in its own commit. A citation key never changes; a document cites a different key only where the owner directs it to another version, switched at adoption. The project's own copy of a style is edited only at adoption and with the owner's approval. Nothing under a project's own source store is moved. A refusal is disclosed, not patched around. A conversion adds no feature to refs; it produces evidence, and a defect it finds is fixed on its own branch.
