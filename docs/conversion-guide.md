# Converting a project to refs

How an existing writing project moves its bibliography into the catalog and takes its reference list back as an export. Written from the family-document pilot and the inventory of 2026-09-26, before the first academic conversion; the findings section at the end grows by one entry per project. Governing rules are in the contracts; this page is the working order.

## When a project qualifies

It has a bibliography file it builds from, kept by hand or by an agent, and the file is not an export from Zotero already in the catalog. The inventory review lists the candidates. A project in the middle of a submission still qualifies, because nothing here changes the project until the export is proven identical in meaning.

## The order

The order has two halves and a stop between them. The first half is read-only and ends in a proposal; nothing in the catalog or the project changes until the owner approves it. The second half executes the approved proposal and stops again only at the export gate. This is so the retypes, versions, unlinks and attachments are decided once, before anything runs, rather than discovered after a gate and redone.

### Propose, read-only

1. **Inventory the project.** Name every bibliography file, who writes it, and every consumer: a Quarto or pandoc build, a LaTeX build with biber or natbib, a venue that demands a `.bib`, a site build, a sync script. Note the citation-key style, since keys must not change. Record which entries the prose cites, so the export can be cited-only later without dropping anything the text uses.

2. **Find the sources.** Read-only in this half: search the stores listed in the attach step below, match by DOI first and then by title, and list what was found with paths, what needs a fetch with the link, and what is URL-only. Nothing is downloaded or moved yet.

3. **Plan the records.** From the bibliography and the sources found, decide per record what the completion step will do: the type the thing is, the kind, protected names, the software version and release date from the rule below, which notes move to context, and what file will be attached from where. Decide the export targets and profiles per consumer and the expected gate outcome per entry, identical or changed with the expected wording.

4. **Stop for approval.** Write the proposal in the report template's first sections: backup name, inventory and consumers, planned import, planned record completions by key, sources found and the fetch list, planned targets and the expected gate outcomes. The owner approves, amends or declines. Only an approved proposal proceeds; an amended one is rewritten and approved again.

### Execute the approved proposal

5. **Backup.** `refs backup --output /Volumes/Casa/refs-backups/<date>-before-<project>-<pass>`, one per pass of a project, named by the pass. Check the manifest validates.

6. **Import.** `refs import --format bib --input references.bib` (or `--format csljson`) with the project named as origin. Read every outcome: applied is new, unchanged is already there, conflict means the catalog holds a different value for a bound source and both are kept for `import reconcile`, invalid names a limit and preserves the entry. Nothing is guessed; a refusal is recorded, not worked around. Where a DOI binds an entry to a source the Zotero import created, the conflict list is the interesting part: it shows where the agent's hand-written entry and the library disagree.

7. **Create and cite the project.** `refs project create <name>` and `refs project cite <name> KEY` for every entry the prose cites, plus the ones the bibliography carries uncited if the owner wants them kept. The export is cited-only, so this list is the reference list.

8. **Complete the records** exactly as approved: One pass over every record before any export gate, so the gate runs once. Is the type what the thing is: a software project cited by its repository is `software`, not `webpage`; documentation is a `webpage` with the site as container title; a scanned order is a `document`. Does a kind apply: `repository` for source code repositories, `podcast`, `lecture` and the rest as the registry lists them. Are software and product names protected in the title, so styles do not recapitalize them. Refs title-cases English titles unless a record preserves its case, so the proposal decides the project's case policy once: title case for academic bibliographies, preserve for archival material whose titles are sentence-case by nature, applied by `title_protection` with `preserve_case` on each record until a per-project policy in `.refs.toml` exists. For software, version and date follow the rule below. Notes hold facts meant for the page; capture provenance and caveats go to context.

9. **Attach the sources** exactly as approved. Every record should end up connected to the thing it describes. Look first in the project folder and its figures, the vault project if there is one, the library at `/Volumes/Casa/refs/lib`, then DEVONthink exports and `~/Downloads`; match by DOI first, then by title. Then by kind of source: an article is fetched by DOI, and open-access publishers have stable PDF locations (JOSE and JOSS by DOI path, PLoS by article id, DOI content negotiation where offered); paywalled and bot-gated hosts, Elsevier and the bepress repositories among them, refuse scripted downloads as a rule and are a browser download by the owner through the university VPN. A software record gets the README at the default branch's current commit and the repository's API metadata, both named with the commit and the date. A web page gets a single-file capture at the accessed date. Files move into the library by `resource add --move`, which names them by the convention and files them under `unfiled` until the loc taxonomy exists; a project's own raw material, such as a vault's scans, stays where it is and is linked in place with loc empty. A source with a scan and a transcription gets two resources with labels; a file linked through `add --file` carries no label, so a project that labels its files attaches them with `resource add --label` until `add` takes a label. The owner's fetches from the approved list are attached the same way; the pass is not complete until every item on the list is attached or disclosed as missing.

10. **Export per consumer, to scratch.** Run `uv run --locked python tests/fixtures/real-trial/conversion_check.py --project <registered-name>`; it reads the register, takes a read-only catalog snapshot, exports through refs into a scratch project copy, runs every consumer, and writes `gate.json` and `gate.md`. Each consumer is rendered by the venue's own pipeline where it runs locally, else by the closest local equivalent, named in the register row so the difference is a known gap; a bibliography gate is valid through the equivalent, since citeproc's reference list does not depend on the venue's layout, while a layout check is not. Never export over the project's file. A pandoc or Quarto consumer takes `--profile csl-json-v1`, the identity mapping; a Pandoc/biber consumer requiring a `.bib` can take `--profile biblatex-v1`, while a classic BibTeX consumer takes `--profile portable-bibtex-v1`. CSL JSON titles may carry CSL's own markup, `nocase` spans for protected case and the `i`, `b`, `sup`, `sub` and `sc` tags; citeproc renders them, and any consumer that formats titles itself from the export, such as a site build, must render or strip them too. Render the project from the scratch export with its own configuration and diff its reference list against the current render, entry by entry. The gate has three outcomes: identical; wording changed by a deliberate type or field correction from step 5, listed per entry with the exact before and after; or a fact lost or altered, which stops the pass until the record or a refs limit explains it. The owner decides adoption once, from the per-entry list. A gate that matches the proposal entry for entry is accepted without discussion; a mismatch in either direction is a finding.

11. **Adopt.** Only after the owner accepts the gate, rerun the same harness command with `--record` to save the current per-consumer fixtures and tool versions. Then export to the project's path, set the bibliography in the build configuration (per format when consumers need different profiles), write `.refs.toml` with the project and one `[[export.targets]]` entry per consumer, each with its own output and profile, and commit those together, separately from any content change. From then on re-exporting the project is `refs export` with no arguments from the project folder, which writes every target in order. Discovery of `.refs.toml` stops at the nearest git root, so a target inside a nested worktree is written from the publication folder, or from inside the worktree with `--project-file` naming the publication's config. Refs remembers the bytes of the last export it published to a target; if that export is later discarded through git, the next export refuses with "Destination differs from recorded export bytes" and needs `--overwrite` after confirming the file on disk matches the commit, and the replaced bytes are kept in the catalog's originals. A legacy file that an earlier tool wrote, such as a venue's `paper.bib` copied by a sync script, is adopted with `--adopt --overwrite` on the condition that its current bytes were imported in step 6; the overwrite acknowledges the planned replacement and the old bytes are kept as originals. When the gate passes, the exported file and the rendered reference-list text become that project's fixture, and the project joins the register below with the refs version and the pandoc and Quarto versions it was verified against.

12. **Retire the hand-kept file** once nothing reads it, in the same commit as the reader's switch, never before. When a generated target replaces the hand-kept file at the same path, adopt it in place; nothing is retired. Run the conversion harness for that project again after changing a reader; a gate alone is not authorization to retire another consumer's input.

13. **Document in the project.** A short `docs/refs.md` in the project: the catalog is the master, the export is generated and never edited, how to add and cite a source, how to re-export, and the checks after every export. Point to it from the project's README and agent instructions.

14. **Report and record.** Write the pass report in the template below, add the findings to this page, and complete the register row. Feature decisions go to the plan's ledger, not to this page.

## Rules the steps rely on

A record links only the source's own file: its PDF, its capture, its scan. A project's synthesis or review note is a project document; a fact from it about one source goes into that record's context.

Every consumer of a project's bibliography gets its own refs target in its own profile. A script that copies one consumer's bibliography to another is the thing the targets replace; it keeps whatever manuscript projection it does and gives up the copy and any byte-equality check on it.

A software record's version is the release current on the record's accessed date, and its issued date is that release's date, both from PyPI or GitHub release history and recorded as a lookup in context, never guessed. Without them Chicago prints "released." with nothing after it.

## After conversion: adding a source

A converted project adds sources through the catalog, never by editing the export. The sequence is the conversion's execution half in small: backup named for the change; the record added as refs JSON with the project's case policy, its file linked or copied and labelled as the project does, and its capture note in context; the key cited in the project; `refs export` with no arguments; the gate run without recording; its diff read, expecting only the new entries and any renumbering; then the record run from a clean tree at a commit, committed on a branch for the review session to merge. A project's own `docs/refs.md` points here and adds only what is particular to that project.

## Report template

Every pass report uses the same headings, so reports diff against each other: backup and scope; inventory and consumers; import outcomes by key; record completions by key; sources found, fetched, and the fetch list for the owner; attachments with final names and hashes; the export gate table with exact before and after per changed entry; commits; timing; findings in two lists, for refs, which become candidate changes in the plan's ledger, and for this guide, which become edits to it. The maintenance sequence above ends with the same two lists. Session reports live under `specs/001-academic-catalog/reviews/` named `<date>-<project>-<pass>.md`.

## Checks

The catalog backup validates; the import's counts sum to the file's entry count and every invalid entry has a named reason; the project's cited count equals the reference list the prose needs; each linked or copied file's hash matches the original; the rendered reference list from the scratch export loses no fact; the build passes after the switch; the project's docs name the export and the re-export command.

After any change in refs to an export profile or a projection, every project in the register is re-exported from the real catalog read-only, re-rendered by every consumer in its row, the style and any hand-rolled formatter alike, and each reference-list text diffed against the last verified render; every difference is listed and explained before the change merges. A difference has two possible causes and the walk cannot tell them apart: refs changed what it exports, or the project changed what it cites. When a project's own content changes its reference list, the session that made the change re-runs the harness for that project and records the accepted render with `--record`, so the fixture follows the project and the next refs change is measured against the current list. Recording is always the second run: the gate runs first without `--record`, its diff is read, and the record run follows from a clean project tree at a commit, naming with `--work` a directory that does not exist yet. The suite tests refs's reading of its own exports and the corpus never renders, so the register is the only check that sees what a style prints. Run `uv run --locked python tests/fixtures/real-trial/conversion_check.py --all` for this walk. The harness stores each project's verified extraction in `converted/<project>/<consumer>.txt`, with publication commit, artifact digest and tool versions in the register. The three mechanical entry outcomes are `identical`, `changed` (exact before/after, including a newly added entry), and `missing`; changed wording still needs human assessment for altered facts. Missing entries, missing fixtures and failed consumers exit nonzero. `--record` asserts owner acceptance and is never part of a normal check; its exit status still describes the pre-record gate. PDF extraction uses the final named References/Sources section, joins wrapped lines and removes page-number footers; entry identities are printed numbers or author/year labels, while site entries use their source keys. A changed PDF entry label therefore appears as missing plus changed, requiring review. Project copies exclude git, caches, worktrees and registered generated outputs; the optional project `inputs` list copies only explicitly named relative files from excluded directories, refusing symlinks, missing files, Git internals and target/artifact collisions. Exports and mutation logs use only the disposable catalog snapshot.

## Boundaries

Prose is never edited for a conversion. Citation keys never change. Nothing under a project's own source store is moved. A refusal is disclosed, not patched around. A conversion adds no feature to refs; it produces evidence.
